## Setup

Add the plugin to your `vite.config.ts`:

```ts
import { defineConfig } from 'vite'
import { okColor } from 'okcolor'

export default defineConfig({
  plugins: [okColor()],
})
```

Every `.css` file processed by Vite will have legacy colors converted to OKLCH automatically. No config needed.

The plugin also handles Vite's virtual style modules, including ids like `Component.vue?vue&type=style&lang.css`. Non-style virtual modules such as Vue templates or scripts are skipped, even if they contain CSS-looking text.

## Options

```ts
interface OkColorOptions {
  /** Inline comment that prevents conversion on that line.
   *  @default 'oklch-ignore' */
  ignoreComment?: string
}
```

The `ignoreComment` option lets you customize the comment that triggers the escape hatch:

```ts
import { okColor } from 'okcolor'

export default defineConfig({
  plugins: [
    okColor({
      ignoreComment: 'keep-legacy',
    }),
  ],
})
```

```css
/* keep-legacy */
.my-color {
  color: #ff0000;
} /* this color stays as hex */
```

Custom ignore comments are restored through a private sentinel, so unrelated `oklch-ignore` text in strings, content, or URLs is not rewritten.

## Supported file types

| Extension          | Processed as | Notes                 |
| ------------------ | ------------ | --------------------- |
| `.css`             | Plain CSS    | Full scan             |
| `.scss`, `.sass`   | Plain CSS    | Preprocessor output   |
| `.less`            | Plain CSS    | Preprocessor output   |
| `.styl`, `.stylus` | Plain CSS    | Preprocessor output   |
| `.vue`             | SFC          | `<style>` blocks only |
| `.svelte`          | SFC          | `<style>` blocks only |
| `.astro`           | Component    | `<style>` blocks only |

For embedded styles, transform failures are reported as `[okcolor]` warnings and the original component source is preserved. That keeps dev servers resilient while still surfacing the problem.

## Scanner boundaries

okcolor transforms colors in real CSS value positions and avoids selector/content corruption:

```css
/* Converted */
@supports (color: red) {
  .btn {
    border: 1px solid #f00;
  }
}

@container style(color: blue) {
  .card {
    box-shadow: 0 0 1rem red;
  }
}

@property --brand {
  syntax: '<color>';
  initial-value: red;
  inherits: false;
}

/* Preserved */
@supports selector(:is(a:hover #abc, .red)) {
  .btn {
    color: green;
  }
}

.motion {
  animation-name: red;
  counter-reset: blue 0;
}
```

The first block has color values, so okcolor modernizes them. The second block contains selector tokens or identifier-only property values, so okcolor leaves them alone.

## Tailwind CSS v4

Tailwind v4 uses OKLCH internally, so okcolor leaves its utilities alone. It only transforms colors in your custom CSS:

```css
/* Input */
.my-button {
  background: #3b82f6;
  border-color: rgb(59 130 246);
}

/* Output */
.my-button {
  background: oklch(61.78% 0.17686 250.43);
  border-color: oklch(61.78% 0.17686 250.43);
}
```

Order in your plugin array does not matter — Vite's plugin system handles CSS pipeline stages correctly regardless of declaration order.
