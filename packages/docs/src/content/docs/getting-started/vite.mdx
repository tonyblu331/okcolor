## Setup

Add the plugin to your `vite.config.ts`:

```ts
import { defineConfig } from 'vite'
import { okColor } from 'okcolor'

export default defineConfig({
  plugins: [okColor()],
})
```

Every `.css` file processed by Vite will have legacy colors converted to OKLCH automatically at build time. No app imports, no client runtime, no shipped okcolor code.

The plugin also handles Vite's virtual style modules, including ids like `Component.vue?vue&type=style&lang.css`. Non-style virtual modules such as Vue templates or scripts are skipped, even if they contain CSS-looking text.

## Options

```ts
interface OkColorOptions {
  /** Inline comment that prevents conversion on that line.
   *  @default 'oklch-ignore' */
  ignoreComment?: string

  /** Token JSON input. When present, token compiler mode is enabled. */
  input?: string

  /** CSS output path for compiled tokens. */
  output?: string

  /** Optional JSON report output path for compiled tokens. */
  reportPath?: string

  /** Fallback and progressive-enhancement targets. */
  targets?: Record<
    string,
    {
      gamut?: 'srgb' | 'p3'
      strategy?: 'convert' | 'expand' | 'grade' | 'fit'
      amount?: number
      format?: 'hex' | 'oklch'
    }
  >

  recipes?: Record<
    string,
    {
      strategy?: 'convert' | 'expand' | 'grade' | 'fit'
      gamut?: 'srgb' | 'p3'
      recipe?: 'literal' | 'vivid' | 'deeper' | 'premium' | 'muted' | 'softer' | 'warmer' | 'cooler'
      amount?: number
    }
  >

  audit?: {
    failOn?: Array<'invalid-css' | 'out-of-gamut' | 'wcag2-regression'>
    wcag2?: {
      level?: 'aa' | 'aaa'
      requiredRatio?: number
    }
  }
}
```

The `ignoreComment` option lets you customize the comment that triggers the escape hatch:

```ts
import { okColor } from 'okcolor'

export default defineConfig({
  plugins: [
    okColor({
      ignoreComment: 'keep-legacy',
    }),
  ],
})
```

```css
/* keep-legacy */
.my-color {
  color: #ff0000;
} /* this color stays as hex */
```

Custom ignore comments are restored through a private sentinel, so unrelated `oklch-ignore` text in strings, content, or URLs is not rewritten.

## Token compiler mode

If `input` and `output` are provided, the plugin compiles design-token JSON during `buildStart` instead of only transforming CSS modules:

```ts
import { okColor } from 'okcolor'

export default defineConfig({
  plugins: [
    okColor({
      input: 'src/tokens/colors.json',
      output: 'src/styles/colors.css',
      reportPath: 'src/styles/okcolor.report.json',
      audit: {
        failOn: ['wcag2-regression'],
        wcag2: { level: 'aa' },
      },
      targets: {
        base: { gamut: 'srgb', strategy: 'convert', format: 'hex' },
        p3: { gamut: 'p3', strategy: 'expand', amount: 0.75, format: 'oklch' },
      },
    }),
  ],
})
```

When `input`/`output` are omitted, okcolor keeps the original zero-config CSS transform behavior.

Token compiler output is layered: sRGB custom properties first, optional OKLCH diagnostics, then Display P3 overrides guarded by `@media (color-gamut: p3)` and `@supports`. If `reportPath` is set, okcolor also writes a JSON report with top-level `schemaVersion: 1`, token diagnostics, pair-level contrast status, WCAG 2 gate results, and APCA advisory values.

WCAG policy is build-time configuration. `audit.wcag2.level` can be `aa` or `aaa`; `audit.wcag2.requiredRatio` overrides both the level and per-token declaration when you need a custom gate.

## Browser runtime adapter

Most apps should never import okcolor from application code. If you are intentionally building a color picker, inspector, playground, or design-system UI that needs live conversion in the browser, use `okcolor/browser`:

```ts
import { colorToOklch, initOkColorBrowser } from 'okcolor/browser'

await initOkColorBrowser()
console.log(colorToOklch('#ff5a00'))
```

| ---------------- | ----- | ------------------------------------------- |

## Supported file types

| Extension          | Processed as | Notes                 |
| ------------------ | ------------ | --------------------- |
| `.css`             | Plain CSS    | Full scan             |
| `.scss`, `.sass`   | Plain CSS    | Preprocessor output   |
| `.less`            | Plain CSS    | Preprocessor output   |
| `.styl`, `.stylus` | Plain CSS    | Preprocessor output   |
| `.vue`             | SFC          | `<style>` blocks only |
| `.svelte`          | SFC          | `<style>` blocks only |
| `.astro`           | Component    | `<style>` blocks only |

For embedded styles, transform failures are reported as `[okcolor]` warnings and the original component source is preserved. That keeps dev servers resilient while still surfacing the problem.

## Scanner boundaries

okcolor transforms colors in real CSS value positions and avoids selector/content corruption:

```css
/* Converted */
@supports (color: red) {
  .btn {
    border: 1px solid #f00;
  }
}

@container style(color: blue) {
  .card {
    box-shadow: 0 0 1rem red;
  }
}

@property --brand {
  syntax: '<color>';
  initial-value: red;
  inherits: false;
}

/* Preserved */
@supports selector(:is(a:hover #abc, .red)) {
  .btn {
    color: green;
  }
}

.motion {
  animation-name: red;
  counter-reset: blue 0;
}
```

The first block has color values, so okcolor modernizes them. The second block contains selector tokens or identifier-only property values, so okcolor leaves them alone.

## Tailwind CSS v4

Tailwind v4 uses OKLCH internally, so okcolor leaves its utilities alone. It only transforms colors in your custom CSS:

```css
/* Input */
.my-button {
  background: #3b82f6;
  border-color: rgb(59 130 246);
}

/* Output */
.my-button {
  background: oklch(61.78% 0.17686 250.43);
  border-color: oklch(61.78% 0.17686 250.43);
}
```

Order in your plugin array does not matter — Vite's plugin system handles CSS pipeline stages correctly regardless of declaration order.
