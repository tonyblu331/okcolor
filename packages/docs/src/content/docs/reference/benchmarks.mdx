The okcolor engine compiles from Rust to WASM via `wasm-bindgen` and processes CSS in a single byte-level pass. No DOM, no regex replacement pipeline, and no allocations beyond scanner state plus the output string.

Benchmarks are workload-sensitive. The docs data can be regenerated from Vitest output in CI, but always compare like-for-like: okcolor scans real CSS while preserving comments, strings, URLs, selectors, modern color functions, embedded styles, and Vite virtual style modules.

Run benchmarks locally:

```bash
npm run bench
```

The numbers below come from `packages/docs/src/data/benchmarks.json`, generated by `scripts/process-benchmarks.mjs`.

## Cache efficiency

The 4096-slot direct-mapped cache means equivalent colors hit the same slot:

| Input 1     | Input 2             | Same physical color  | Cache hit |
| ----------- | ------------------- | -------------------- | --------- |
| `#ff0000`   | `rgb(255, 0, 0)`    | Yes                  | Yes       |
| `#ff0000`   | `red`               | Yes                  | Yes       |
| `#ff0000`   | `hsl(0, 100%, 50%)` | Yes                  | Yes       |
| `#ff000080` | `#ff0000`           | No (different alpha) | No        |

The cache key packs `(r, g, b, a)` into a single u32. Hash is `key % 4096` via bitmask.

## Why Rust/WASM?

The scanner does not allocate intermediate color objects. It walks the input byte-by-byte, dispatching to typed matchers at word boundaries. The gamma decode uses a precomputed 256-entry lookup table. All math is inlined with no function call overhead for hot paths.

The stateful scanner tracks declaration blocks, `@supports` and `@container` value contexts, selector-function depth, `@property` color syntax, and property-level named-color eligibility. That keeps correctness high without repeatedly rescanning generated selector lists.

The single-pass design means the engine touches each byte predictably — compare with regex-based approaches that may backtrack, scan multiple times, or rewrite tokens inside selectors and strings.
